# 화면 설계

`NIT_train` 파이프라인을 사람이 실제로 끝낼 수 있게 만드는 것이 이 콘솔의 목적이다.
API 를 그대로 노출한 관리 도구가 아니라, **작업 순서를 화면이 강제하는** 구조로 만들었다.

---

## 1. 전체 원칙

### 탭 번호가 파이프라인 순서

`1 영상 → 2 구간 → 3 라벨링 → 4 데이터셋 → 5 학습 → 6 모델`.
각 화면 우상단에 다음 단계 버튼이 있고, 작업이 끝나면 다음 화면으로 자동 이동한다
(프레임 추출 완료 → 라벨링, 데이터셋 빌드 완료 → 상세 → 학습).
"이제 뭘 눌러야 하지" 를 고민하게 만드는 순간 파이프라인은 안 쓰인다.

### 단계 간에 넘기는 상태는 "작업 중인 영상" 하나

상단 칩에 항상 표시되고 `localStorage` 에 남는다. 새로고침해도 작업 맥락이 유지된다.
그 외의 상태는 각 화면이 자기 것만 갖는다 — 전역 상태 관리를 도입할 이유가 없다.

### 빌드 도구 없음

폐쇄망 배포에서 `npm install` 이 막히는 경우가 많다. ES 모듈 + CSS 만 쓰면 배포가
"이 폴더를 정적 서빙" 으로 끝난다. `view` 모듈은 `render()` 를 내보내고 필요하면
`{ dispose }` 를 돌려준다. 라우터가 화면 전환마다 `dispose()` 를 호출하므로 타이머·
키 리스너·폴링이 다른 화면으로 새지 않는다.

### 어두운 테마 고정

화면의 주인공은 프레임 이미지와 색이 있는 라벨 박스다. UI 를 어둡게 낮추면 밝은 프레임과
클래스 색이 튀어 보인다. 클래스 색은 서버 오버레이(`annotations.color_for`)와 **같은
황금비 분할**을 쓴다. 썸네일(서버가 그린 JPEG)과 캔버스(프런트가 그린 박스)의 색이
다르면 사용자가 다른 객체라고 착각한다.

---

## 2. 1 · 영상

업로드와 "서버 경로 등록" 을 나란히 둔다. 수십 GB 드론 영상을 브라우저로 다시 올리는 것은
낭비다. NAS/서버에 이미 있는 파일은 경로만 등록해 복사 없이 파이프라인에 넣는다.

업로드는 `fetch` 가 아니라 `XMLHttpRequest` 를 쓴다. 진행률이 없으면 사용자가 멈춘 줄 알고
새로고침한다. 여러 파일은 **순차**로 보낸다 — 동시 업로드는 디스크 쓰기를 서로 방해해
전체 시간이 오히려 늘어난다.

카드에 구간 요약과 라벨링 진행률을 함께 띄운다. 목록만 보고도 "어느 영상이 어디까지
됐는지" 가 보여야 여러 영상을 병행할 수 있다.

---

## 3. 2 · 구간

요구의 핵심(정상 여러 개 / 비정상 여러 개)을 두 가지 조작으로 만들었다.

- **키보드 마킹**: 재생하면서 `I`(시작) → `O`(끝). 수십 분짜리 영상을 훑을 때 손이
  마우스로 옮겨가지 않는 이 방식만이 견딘다.
- **타임라인 드래그**: 이미 아는 구간을 빠르게 긋는다. 짧게 클릭하면 그 지점으로 탐색한다.

타임라인은 정상(위·초록)과 비정상(아래·빨강)을 다른 줄에 그린다. 겹치는 관계가 눈에 보여야
"비정상이 정상을 이긴다" 는 규칙을 이해할 수 있다. 저장하면 서버가 병합·차집합을 계산해
`selection_ranges` 를 돌려주고, 화면은 **실제 추출 대상**을 그대로 보여준다.
프런트가 같은 계산을 다시 구현하면 두 곳이 어긋난다.

영상 탐색(seek)은 API 가 HTTP Range 를 처리해야 가능하다. 그래서 계약 테스트에서
206 응답을 확인한다.

추출은 잡이다. 새로고침해도 진행률이 이어지도록 화면을 열 때
`GET /api/jobs?kind=extract&target=<video>` 로 진행 중인 잡을 찾아 다시 붙는다.

---

## 4. 3 · 라벨링

프레임이 수천 장이므로 **장당 작업량을 줄이는 데 전부를 건다.**

### 세 칸 배치

- 왼쪽 필름스트립: 서버가 라벨을 그려 준 오버레이 썸네일(`?overlay=1`). 상태별 색으로
  남은 일이 한눈에 보인다. `loading="lazy"` 로 보이는 것만 받는다.
- 가운데 캔버스: 원본 프레임 + 프런트가 그린 박스. 확대/이동 지원.
- 오른쪽: 이 프레임의 객체 / 객체(track) 일괄 지정 / 클래스 / 단축키.

### 공수를 객체 수에 비례하게

`track_id` 가 붙어 있으면 오른쪽 패널에서 클래스를 한 번 고르는 것으로 그 객체가 등장하는
**모든 프레임**에 전파된다(`POST /api/videos/{id}/propagate`). 300 프레임에 나오는 전차
1대는 클릭 한 번이다. 이것이 없으면 라벨링은 프레임 수에 비례해 사실상 불가능해진다.

### 회전박스는 항상 직사각형

편집 중에는 `{cx, cy, w, h, angle}` 로 다루고 저장할 때만 4점으로 되돌린다(`obb.js`).
4점 자유 이동을 허용하면 조금만 잘못 끌어도 사다리꼴이 되고, 그 라벨은 YOLO OBB 학습에서
**에러 없이** 이상한 각도로 해석된다. 조작별 규칙은 이렇다.

| 조작 | 규칙 |
| --- | --- |
| 꼭짓점 드래그 | 반대쪽 꼭짓점을 세계 좌표에 고정하고 폭/높이/중심만 다시 계산. 각도 불변 |
| 회전 핸들 | 핸들이 항상 "위쪽" 을 가리키도록 각도 계산 |
| 경계 초과 | 잘라내지 않고 **평행이동**으로 되돌린다. 회전 박스를 클램프하면 사각형이 깨진다 |

이 규칙들은 `test/obb.test.js` 에서 네 각이 90°인지까지 검사한다.

### 미확정은 점선

클래스가 정해지지 않은 객체는 점선 + 주황 표시로 남긴다. 서버가 승인 시점에
"모든 객체에 클래스가 있어야 한다" 를 강제하므로, 남은 일이 화면에서 보여야 한다.

### 작업을 잃지 않는다

프레임을 넘기거나 필터를 바꾸거나 화면을 떠날 때 수정 중이던 라벨을 자동 저장한다.
브라우저를 닫으려 하면 `beforeunload` 로 확인을 띄운다. 라벨링 도구가 작업을 잃는 것은
어떤 이유로도 용납되지 않는다.

## 5. 4 · 데이터셋

산출물은 `tracker_py/train_data/preprocessed_obb` 와 같은 구조다.
그래서 화면도 그 구조를 중심으로 셋으로 나뉜다.

1. **빌드** — 승인된 라벨을 모아 새로 만든다.
2. **등록** — 이미 있는 그 구조의 폴더를 그대로 올린다. `확인` 버튼으로 태스크·클래스·장수를
   먼저 읽어 보여주고(`GET /api/datasets/inspect`), 현재 클래스 목록에 없는 이름이 있으면
   경고한다. 복사하지 않는 것이 기본이다(수천 장 중복 저장 방지).
3. **병합** — 빌드할 때 기존 데이터셋을 같이 넣는다. 영상을 하나도 고르지 않고 병합 소스만
   주면 "기존 데이터셋만" 이 된다.

분할 기본값이 `chunk` 인 이유를 화면에 적어 둔다. 인접 프레임은 사실상 같은 그림이라
무작위로 나누면 train/valid 에 같은 장면이 들어가 검증 점수가 부풀려진다.
병합해 들어온 기존 데이터셋은 **원래 분할을 유지**한다 — 남의 valid 를 내 train 으로
섞으면 과거 실험과 점수를 비교할 수 없다.

상세에는 클래스 분포 막대, `data.yaml` 원문, 병합 이력(어느 폴더가 어떤 접두사로
들어갔고 클래스가 어떻게 매핑됐는지), 제외된 프레임의 사유를 모두 띄운다.
학습을 돌리기 전에 데이터를 눈으로 확인하는 것이 가장 값싼 디버깅이다.

---

## 6. 5 · 학습

학습은 몇 시간짜리다. 그래서 "시작 버튼" 이 아니라 **감시 콘솔**로 만들었다.
목록과 상세를 3초마다 갱신하고, 로그는 사용자가 위로 스크롤해 읽고 있으면 자동으로
맨 아래로 끌어내리지 않는다.

시작 폼에서는 데이터셋 태스크와 가중치 태스크가 어긋나면 미리 경고한다
(회전박스 데이터셋에 축정렬 가중치를 넣으면 학습 시작 직후 실패한다).
`workers` 기본값이 4인 이유도 적어 둔다 — Windows spawn 은 워커마다 RAM 을 물어
후반 epoch 에서 DataLoader 가 죽는다.

승격은 상세 안에서 한다. 지표를 보고 있는 자리에서 이름을 붙이는 것이 자연스럽고,
"어떤 run 의 어떤 지표로 승격했는지" 를 사용자가 기억할 필요가 없어진다.

---

## 7. 6 · 모델

`test_model/`(사전학습) · `workspace/models/`(승격) · `runs/*/weights/`(학습 산출물)를
모두 한 표에 모은다. 자동 라벨과 학습의 선택 목록이 결국 이 목록이기 때문이다.

승격 이력에는 출처(데이터셋·run·기반 가중치)와 지표를 함께 남긴다.
"모델 파일만 남고 출처를 아무도 모르는" 상황을 막는 것이 승격의 존재 이유다.

---

## 8. 알려진 제약

- **첫 자동 라벨은 비어 있다.** 사전학습 COCO/DOTA 가중치는 탑다운 드론 영상의 10px
  표적을 conf 0.05 에서도 하나도 못 잡는다(실측). 기존 라벨 데이터셋으로 한 번 학습해
  승격한 모델을 초안 생성에 써야 한다. 화면에 이 안내와 경고 토스트를 넣어 두었다.
- 필름스트립은 최대 1,000장까지 받아 그린다. 그보다 많으면 상태 필터로 좁힌다.
- 프레임 이미지·오버레이는 매 요청마다 서버가 디코딩한다. 수천 장을 빠르게 훑으면
  API 가 그만큼 일한다(별도 썸네일 캐시는 두지 않았다).
